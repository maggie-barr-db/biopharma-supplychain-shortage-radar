# DECISIONS.md - decisions and evaluation protocol

I made each of these decisions on 2026-11-21 from options my AI pair engineer laid out with trade-offs. The reasoning is mine.

| # | Decision | Chosen | Alternatives considered | Why |
|---|---|---|---|---|
| 1 | Ingestion | Auto Loader (`read_files`) over files landing in a UC volume | Lakeflow Connect to a live source; JDBC | I prefer files landing in a governed volume: it mirrors how ERP and quality extracts arrive at most manufacturers, and a file-arrival trigger lets the pipeline react to a new disruption signal. Lakeflow Connect would be the production path for SAP. |
| 2 | Sources | Two systems merged (ERP + supplier quality) | One source | Two sources is the better real-life scenario. Supplier codes that don't match ERP vendor IDs are exactly the kind of data quality problem that makes impact assessment take days, so conforming them is part of the value. |
| 3 | Data quality | Quarantine duplicate PO lines and negative forecasts; warn and track missing lead times, schema changes (rescued data) and late or missing feeds; fail the update on missing keys | Drop all bad rows; warn only | Data quality has to protect integrity and still let the job finish. Quarantined duplicates can be revisited later. Missing data gets a warning and is tracked so it can be supplied later, and a new or mistyped field lands in `_rescued_data` instead of silently changing the schema. A missing key breaks referential integrity, so the update stops: pushing bad data downstream is much harder to clean up, risks bad decisions and destroys trust in the data. |
| 4 | Personas | `planner_us`, `planner_eu` (own region, price and revenue masked), `supply_exec` (all regions, commercial values visible, approves) | Two groups only | Planners own days of cover, replenishment, allocation when supply is short and the inputs to S&OP. They work in units, dates and lead times and can do all of that without price or revenue, so that data stays masked and filtered for them because it is commercially sensitive at BioChain. The VP Supply Chain makes the spending decisions and reports revenue at risk to the executive committee, so they see it. |
| 5 | Access test identity | Service principal in `planner_eu` | A second human user | It is scriptable and repeatable, so the access test output can be committed as evidence. |
| 6 | Lakebase pattern | Synced table from gold for reads + native Postgres tables for decisions and audit | Synced only; job upserts only | Human decisions need fast, isolated transactions: when several people approve at once, each write must commit in milliseconds without colliding. Writing each decision to Delta through a warehouse would be slow and conflict-prone. Lakebase also lets the database enforce the rules itself (approval trigger, row-level security, no deletes), which is what a Part 11 conversation cares about. |
| 7 | Intelligent step | Trained late-PO classifier + `ai_query` explanations + an agent that proposes mitigations | Score + ai_query only; model only | I wanted AI to influence the workflow, not decorate it. The model changes the numbers (projected days of cover), the LLM explains the impact in planner terms, and the agent drafts the action a person then approves. |
| 8 | AI evaluation | Time-split holdout vs a baseline; Genie benchmark questions; groundedness check on explanations | Manual spot checks | Spot checks don't give measurable results or test coverage as the data and code change. The executive has to trust the numbers, and without repeatable tests you can't predict or prevent inaccurate data or a break that takes down the planning team. The tests are repeatable scripts today; running them in CI on every change is the next step. |
| 9 | Evaluation rules first | Baseline, holdout, main measure and the no-claim threshold written below (Evaluation protocol) before any result | Decide what good looks like after seeing results | Success should be measured against acceptance criteria and KPIs agreed up front, not retrofitted after the product is built; it stops you moving the goalposts after you see results. Every later change is a dated note and the original results stay. |
| 10 | App | FastAPI + React, Databricks-branded | Streamlit | React is the better tool if this becomes a reusable asset, and it keeps a clean API between the UI and the data. |
| 11 | Routing | Code agent from the Agent Bricks CLI: two Genie Agents and a `propose_mitigation` Lakebase tool, request-user auth, MLflow tracing | Genie One across both agents; one Genie Agent with a docs volume | I wanted prescriptive, rule-guided routing to specific Genie Agents rather than letting Genie One decide. The agent is still an LLM making the call, but it follows explicit routing rules and is graded on them (15 of 15). It also lives inside my app, so a planner can chat with the data, write back a decision and see the impact in one place; Genie One is a separate surface. Supervisor Agent and Knowledge Assistant are legacy as of November 2026. |
| 12 | Security model | Classic UC row filters and column masks driven by an entitlement table; Postgres RLS in Lakebase | ABAC with governed tags | I would have preferred ABAC, but this workspace had no governed tags left. For a customer I'd position filters and masks as the short-term answer if ABAC isn't approved yet by enterprise architecture and security, and recommend moving to ABAC with governed tags for scale. The entitlement design maps straight onto ABAC (region and commercial attributes become tags), so the move is a policy change, not a redesign. UC policies don't apply to queries that go straight to Postgres, so Lakebase keeps its own RLS either way. |
| 13 | Decisions back to the lakehouse | A job task lands Lakebase decisions and audit rows into governed Delta (`gold.mitigation_decision`, `gold.mitigation_audit`) on every run; the native Lakebase change data feed (Beta) is configured as the target path | Keep decisions only in Lakebase; rely on the Beta feed alone | Approved mitigations become important data outside this app (S&OP, audit, supplier reviews), so they should land in Delta under the same region filter and revenue mask. The change data feed needs a storage-backed catalog (it rejects Default Storage), so it writes to `supply_chain_decisions`; it had not materialized tables in this workspace yet, so the job task is what lands the data today. |

## Evaluation protocol (written 2026-11-21, before any result)

Later changes are dated notes; original results are kept in BUILD_LOG.md and evidence/.

- **Late-PO model.** Question: will an open API PO line arrive more than 7 days late? Baseline: the vendor's trailing 12-month on-time rate. Holdout: the most recent 3 months of PO lines by order date; training uses only earlier lines. Timing rule: features use only what was known at PO creation. Main measure: PR-AUC (secondary: recall in the top 20% riskiest lines). No claim if the model beats the baseline by less than 0.05.
- **Genie and routing.** 15 questions written before tuning (12 with an expected SQL answer in `src/genie/*.geniespace.json`, 3 cross-agent in `tools/eval_genie.py`). Bars: 80% of answers correct, 13 of 15 routed to the expected tool; one rerun allowed. Access check: 3 questions rerun as the EU planner must show EU only and no revenue.
- **ai_query explanations.** Every number in an explanation must appear in its source row; any ungrounded number fails.

**Results:** model PR-AUC 0.562 vs 0.455 (lift 0.107, claim holds); Genie 11 of 12 correct, routing 15 of 15; explanations 25 of 25 grounded.

**Change notes (2026-11-21)**
- Before training: labels only count once a line has had time to arrive (promised date at least 45 days before the as-of date), so late lines not yet received don't make the holdout look easy. Dropped an "open event" feature because its status reflects today, not the order date.
- Explanations, first run: 6 of 25 grounded. The checker kept trailing commas ("2027-01-11,"); fixed, the same 25 re-scored 25 of 25.
- Genie, first run: 10 of 12. Both misses were answer-key errors (a NULL on-time rate sorted first; a ranking with ties). Fixed the key; added an instruction never to show masked revenue as 0. After the rerun: 11 of 12; the remaining miss is the tied ranking.
